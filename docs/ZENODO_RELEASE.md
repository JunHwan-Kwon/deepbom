# Zenodo Release Procedure

## Records

Publish two linked records:

1. `Software`: a versioned citation and provenance record for the hosted
   DEEPBOM release. Record metadata is public; files are restricted.
2. `Dataset`: public, non-code supported-format validation evidence generated
   by the exact software release commit.

Use the software version DOI when reproducibility depends on a specific
release. Use the software concept DOI for release-independent references. Cite
both records when a claim also depends on the published validation evidence.

## Software-record scope

The software archive is a restricted provenance dossier containing only:

- `.zenodo.json` and `CITATION.cff`;
- `CHANGELOG.md`;
- `docs/SOFTWARE_RECORD.md`;
- the evidence/reproducibility statement.

This internal release procedure remains in the private repository and is not
included in the uploaded citation dossier.

It must not contain source code, JavaScript application modules, WebAssembly or
native binaries, package lockfiles, private repository content, model files,
credentials, collectors, schemas, tests, or protected report logic. The
archive is not a source distribution and must not be described as one.

## Prepare

1. Confirm `package.json`, `Cargo.toml`, `CITATION.cff`, and `.zenodo.json` use
   the same semantic version.
2. Confirm creator name, ORCID, affiliation, release date, title, description,
   and restricted access conditions.
3. Run the complete repository checks and supported-format browser validation.
4. Commit all release changes and verify `git status --porcelain` is empty.
5. Create and push the signed or annotated release tag `vX.Y.Z`.
6. Re-run supported-format validation from the tagged clean worktree.

## Build

```powershell
npm run check:zenodo
npm run build:zenodo
npm run build:zenodo:validation
```

The command writes candidates under `.local-validation/zenodo-citation/`, kept
separate from any obsolete source-archive drafts:

- upload the citation-record ZIP to a Zenodo Software record with file
  visibility set to `Restricted`;
- upload the validation-evidence ZIP to a separate public Dataset record; and
- keep adjacent checksum and summary files locally for pre-upload verification.

Do not upload any older `*-source*.zip` generated by an earlier release policy.

release files. After reservation, add it to `CITATION.cff` and record metadata,
rebuild from a clean commit, and compare the resulting ZIP SHA-256 before
publication.
